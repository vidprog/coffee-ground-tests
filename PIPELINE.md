# SDLC-пайплайн на агентах

Демо-версія життєвого циклу розробки, де рутину виконує Claude Code, а рішення ухвалює людина.

## Принципи

1. **Стан живе в лейблах.** Агент не памʼятає попередні запуски. Лейбли — єдине джерело правди.
2. **Мердж завжди робить людина.** Агент доводить роботу до PR і зупиняється.
3. **Докази, а не обіцянки.** Кожна заявка «працює» супроводжується тестом і скріншотом.
4. **Невпевненість — не сором.** Краще `needs-human` з гіпотезами, ніж вигаданий фікс.

     └───────┬───────┘                   └────────────┘

      ┌──────┴───────┐

      ▼              ▼
┌───────────┐   ┌──────────────┐

      │                │ spec:ready
      │                ▼
      │         ┌──────────────┐
      │         │ РЕЦЕНЗІЯ 👤  │  людина ставить spec:approved
      │         └──────┬───────┘
      │                │ spec:approved
      ▼                ▼

## Лейбли

| Лейбл | Значення | Хто ставить |
|---|---|---|
| `ai:triaged` | тікет класифіковано | тріаж |
| `type:bug` / `type:feature` / `type:other` | тип тікета | тріаж |
| `needs-info` | бракує даних, чекаємо автора | тріаж, аналіз |
| `ai:in-progress` | агент працює просто зараз | будь-який етап |
| `bug:reproduced` | баг відтворено, кроки підтверджені | репро |
| `bug:not-reproducible` | відтворити не вдалося | репро |
| `spec:ready` | специфікація написана, чекає людину | специфікація |
| `spec:approved` | людина схвалила | **людина** |
| `needs-human` | низька впевненість або блокер | будь-який етап |
| `ai:reviewed` | AI-рев'ю пройдено | рев'ю |

## Як людина керує пайплайном

Автоматичного тригера немає: коментар у тікеті сам по собі нічого не запускає.
Стан міняють **лейбли**, а етап запускає людина — відкриває Claude Code і викликає скіл.

| Що треба | Як це зробити |
|---|---|
| схвалити специфікацію | поставити лейбл `spec:approved` — в UI або `gh issue edit <N> --add-label "spec:approved"` |
| повернути специфікацію на переписування | зняти `spec:ready`, написати причину коментарем, запустити скіл `feature-spec` |
| перекласифікувати тікет | зняти `ai:triaged`, запустити скіл `triage` |
| повторити спробу відтворення | запустити скіл `bug-agent` |
| припинити роботу над тікетом | перервати сесію і зняти лейбл `ai:in-progress` руками |

Коментар із поясненням «чому схвалено» чи «що саме не так» лишається корисним:
наступний етап читає всі коментарі людини після специфікації і вважає їх частиною
завдання. Але вмикає етап лейбл і запуск скіла, а не текст коментаря.

## Рубрика впевненості

Агент виправляє баг **сам** лише якщо виконано **всі** умови:

- причину локалізовано в конкретному рядку або функції;
- є Playwright-тест, що падає до фікса і проходить після;
- зміна зачіпає ≤ 2 файли і не змінює структуру даних `TESTS`;
- фікс не потребує вибору між кількома продуктовими варіантами.

Інакше — `needs-human` + коментар із гіпотезами, доказами й тим, що саме заблокувало.

## Формат доказів

Скріншоти комітяться в гілку PR у `docs/evidence/` і вставляються в коментар
за посиланням `https://raw.githubusercontent.com/vidprog/coffee-ground-tests/<гілка>/docs/evidence/<файл>.png`.

Артефакти GitHub Actions для цього не годяться — їх не видно в коментарі.

Для бага обовʼязкові два скріншоти: **до** (баг видно) і **після** (баг зник),
плюс тест, що це фіксує. Скріншот сам по собі доказом фікса не вважається.

## Гілки й PR

- гілка: `ai/<номер>-<короткий-опис>` (наприклад `ai/12-fix-mobile-overflow`);
- один тікет — один PR;
- в описі PR обовʼязково `Fixes #<номер>`;
- PR створюється як draft, стає ready тільки коли тести зелені.

## Чого агент не робить

Мердж, пуш у `main`, зміни `.github/` та `.claude/`, зміни налаштувань репозиторію,
нові рантайм-залежності, робота над тікетом із лейблом `needs-human` без явної команди людини.

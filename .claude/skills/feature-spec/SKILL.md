# Специфікація фічі

Твоя робота — **дослідити й описати**, не реалізувати. Код фічі на цьому етапі не пишеться.
Результат читає людина і вирішує: ставити `spec:approved` чи повернути на переписування.

Номер тікета в `$ISSUE`.

## Крок 0. Перевір стан

Працюй лише якщо є `type:feature` + `ai:triaged`, і немає `spec:ready`, `spec:approved`,
`ai:in-progress`, `needs-info`. Постав `ai:in-progress`, зніми наприкінці.

Виняток: людина прямо попросила переписати — тоді переписуй, навіть якщо `spec:ready` вже стоїть.

## Крок 1. Дослідь

Прочитай `CLAUDE.md`, потім реальний код у зоні зміни. Конкретно зʼясуй:

- де саме в поточному коді живе ця поведінка (файл і функція);
- що вже є готового, що можна перевикористати;
- які обмеження накладає чистий фронтенд без збірки (немає сервера, немає стану між сесіями);
- чи не конфліктує це з `prefers-reduced-motion`, адаптивом, українською локалізацією.

Специфікація без посилань на конкретні рядки коду — вигадка. Так її й оцінять.

## Крок 2. Намалюй макет — справжнім скріншотом

Псевдографіка в коментарі **заборонена**. Людина мусить побачити результат очима,
а не реконструювати його з рамок і рисок.

Макет робиться **накладенням на живу сторінку**, а не правкою файлів проєкту:

1. Напиши одноразовий скрипт у `/tmp` (у репозиторій він не потрапляє).
   Node не знайде звідти `node_modules` проєкту — підключай Playwright через
   `createRequire("<корінь проєкту>/package.json")`, а не звичайним `import`.
2. Підніми сайт як є, відкрий у Playwright — той самий Chromium, що й у тестах.
3. Наклади запропоновану зміну в рантаймі: `page.addStyleTag`, `page.evaluate`,
   `context.addInitScript`. Файли `index.html`, `styles.css`, `app.js` **не чіпай**.
4. Зніми мінімум дві ширини: десктоп 1280 і мобільну **360** — ту саму, що в критеріях приймання.
5. Якщо зміна має стани (увімкнено/вимкнено, до/після) — покажи обидва.

Імена файлів: `docs/evidence/spec-$ISSUE-<екран>[-mobile].png`.
Конвенція іменування — у `.claude/skills/_shared/evidence.md`.

Далі поклади PNG у гілку, щоб raw-посилання працювало. Гілка **тільки з картинками**,
без коду і без PR:

```bash
git worktree add /tmp/mockup-$ISSUE -b ai/$ISSUE-spec-mockup origin/main
cp docs/evidence/spec-$ISSUE-*.png /tmp/mockup-$ISSUE/docs/evidence/
git -C /tmp/mockup-$ISSUE add docs/evidence/
git -C /tmp/mockup-$ISSUE commit -m "Макет до специфікації #$ISSUE"
git -C /tmp/mockup-$ISSUE push -u origin ai/$ISSUE-spec-mockup
git worktree remove /tmp/mockup-$ISSUE
```

Worktree — щоб не тягнути за собою незакомічені зміни з робочої гілки.

Посилання в коментарі:
`https://raw.githubusercontent.com/vidprog/coffee-ground-tests/ai/$ISSUE-spec-mockup/docs/evidence/spec-$ISSUE-home.png`

**Макет мусить бути чесним.** Це накладення на справжню верстку справжнього проєкту,
тож він показує реальні пропорції, шрифти й поведінку на 360px. Якщо домальовуєш те,
чого в проєкті немає, — скажи це в підписі під картинкою.

## Крок 3. Напиши специфікацію

Коментарем у тікет, рівно в такому форматі:

```markdown
## 📋 Специфікація

### Хто і навіщо
Користувач, сценарій, проблема. Одне-два речення.

### Що робимо
Опис поведінки з погляду користувача. Без слів «оптимізувати», «покращити» —
тільки те, що можна побачити на екрані.

### Як це виглядатиме

| Десктоп | 360px |
|---|---|
| ![десктоп](https://raw.githubusercontent.com/vidprog/coffee-ground-tests/ai/$ISSUE-spec-mockup/docs/evidence/spec-$ISSUE-home.png) | ![мобільний](https://raw.githubusercontent.com/vidprog/coffee-ground-tests/ai/$ISSUE-spec-mockup/docs/evidence/spec-$ISSUE-home-mobile.png) |

Під картинками — один рядок про те, що саме на них видно і що домальовано.

### Критерії приймання
- [ ] Кожен пункт перевіряється Playwright-тестом.
- [ ] Формулюй як спостережувану дію: «після кліку на X зʼявляється Y».
- [ ] Обовʼязково пункт про мобільну ширину 360px.
- [ ] Обовʼязково пункт про `prefers-reduced-motion`, якщо є анімація.

### Поза межами
Що свідомо НЕ робимо в цьому тікеті. Мінімум два пункти.

### Технічний план
| Файл | Зміна |
|---|---|
| `app.js` | нова функція `shareResult()` біля `copyResult()` (рядок ~118) |
| `styles.css` | стиль кнопки на основі `.ghost-btn` |
| `tests/share.spec.js` | новий тест на критерії приймання |

Оцінка розміру: S / M / L. Ризики: що може піти не так.

### Відкриті питання
Те, де потрібне рішення людини. Якщо питань нема — напиши «нема».

---
👤 **Потрібна рецензія.** Згоден — постав лейбл `spec:approved`, і можна братися за імплементацію.
Щось не так — напиши коментарем, специфікацію перепишу.

<sub>🤖 Автоматична специфікація · макет накладено в браузері, код проєкту не змінювався</sub>
```

## Крок 4. Постав лейбли

```bash
gh issue edit $ISSUE -R vidprog/coffee-ground-tests \
  --add-label "spec:ready" --remove-label "ai:in-progress"
```

## Якщо специфікацію повернули

Прочитай причину, перепиши специфікацію **з урахуванням саме цього зауваження**,
познач у коментарі, що змінилося порівняно з попередньою версією, і перезніми макет,
якщо зауваження стосувалося вигляду. Не сперечайся, але якщо зауваження суперечить коду —
скажи це прямо, з посиланням на рядки.

## Заборонено

Писати код фічі, правити файли проєкту заради макета, відкривати PR,
ставити `spec:approved` самому, робити припущення про бекенд чи збірку — їх у проєкті немає.
Псевдографіка замість скріншота. Малювати макет у графічному редакторі замість браузера —
він збреше про пропорції.

Гілка `ai/$ISSUE-spec-mockup` з самими лише PNG — єдине, що цьому скілу дозволено пушити.
